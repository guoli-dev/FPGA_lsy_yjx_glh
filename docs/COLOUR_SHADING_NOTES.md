# 径向色偏（四周偏红 / 中间偏绿）调查记录

> 状态：**未解决，已暂停**。当前固件使用固定系数表，实测可接受。
> 本文记录查到了什么、排除了什么、哪些做法是错的 —— 避免下次从零重来。

---

## 1. 现象

对着白纸/白墙时，画面呈现**一圈椭圆的粉红**：中心接近中性，中环偏红，四角反而略偏绿。

同时伴随两个次生现象：

- 白色物体在画面边缘偏红
- 绿色色块在远离中心时识别不到（AWB 把 R/B 抬升后，绿色的相对饱和度被吃掉）

---

## 2. 物理成因：镜头色阴影（lens colour shading）

判定依据：

1. 用手机拍屏幕白场，把屏幕四角做透视校正后按半径分区统计 R/G：

   | zone | 位置 | R/G 相对中心 |
   |---|---|---|
   | 0 | 中心 | 1.000 |
   | 3 | | 1.024 |
   | **5** | **中环** | **1.037** ← 峰值 |
   | 7 | | 1.024 |
   | 9 | | 1.004 |
   | **11** | **四角** | **0.971** ← 比中心更绿 |

2. 曲线**不是单调向外加深**，而是中环隆起、四角回落 —— 与"一圈粉红"一致。

3. 残留幅度只有 **±3% 量级**，比最初估计的 10~17% 小得多。

### 一个尚未排除的干扰

两张照片都显示**左侧比右侧红约 8%**。真正的镜头阴影是轴对称的，左右必须相等，所以这部分大概率不是图像问题，而是：

- 屏幕（LCD）的**视角色偏**——从侧面看时左右不对称
- 或手机拍摄角度造成的伪影

**验证方法（未做）**：人站到屏幕正前方居中，再看白场画面。如果左侧变红消失，说明是屏的视角特性，**FPGA 不应该去修它**（修了反而让正面看的人觉得偏色）。

---

## 3. 已排除的假设

| 假设 | 结论 | 依据 |
|---|---|---|
| AWB 除法器算错 | **排除** | 顺序除法器与 `floor((sum_g<<16)/sum_r)` 逐位比对，3506 例 0 失配 |
| AWB 是全局增益，修不了径向 | **确认成立** | 灰世界只对齐全帧均值，结构上无法表达空间梯度 |
| 我加的 tint 造成偏色 | **排除** | 系数全置 0（纯旁路）时画面**照样偏红** |
| 传感器片内 LSC 可以解决 | **排除** | 见第 4 节 |
| SC500 寄存器表可以抄 SC520 | **排除** | 78 个共同地址只有 42.3% 值相同；SC520 多出的 86 个地址集中在 `0x57xx/0x59xx/0x5Axx` |

---

## 4. 参考项目（cz666GOUTOU）调研结论

**他们没有解决这个问题。**

| 项 | 事实 |
|---|---|
| 其 README 系统图 | 摄像头写的是 **SC500CS**，配置走 `uics500_cfg/` |
| 其 SC500 配置表 | **一条 `0x57xx` 都没有**（最大地址 `0x5000`） |
| `0x578x~0x57AA` 十条 LSC 寄存器 | 只存在于 **`uics520_cfg/`**，且无任何注释（厂商参考表原样拷贝） |
| 其 FPGA LSC（`raw10_lsc.v`） | 表格**全 1.0 = 关闭**，注释原文：<br>`NO measured gains yet... this is NOT a colour correction preset` |
| 全仓库文档 | 关于 LSC / 阴影 / 标定 **一个字都没有** |
| 是否上板验证 | README 明写"**未重新综合、布局布线或上板验证**" |

**唯一值得借鉴的是模块结构**（不是参数）：

- 位置在 **RAW 域**（demosaic 之前），逐 Bayer 平面独立 —— 原理上比在 RGB 域做更正确
- 每平面 6×4 = 24 节点，Q2.10（1024 = 1.0）
- 双线性插值用**加法递推**，0 DSP
- 关闭时走 unity 快速通道，零面积
- 表放在单独的 `_config.v`，改表不碰主模块

## 5. 失败尝试记录

按时间顺序，每次只动一个变量：

### 第 1 版：单向压红（只降 R、只加 G）
- 结果：四角变好，但**全屏发绿**
- 原因：表是单向的，平均值被推动；而 AWB 在 tint **上游**，看不到这个偏移

### 第 2 版：双向带符号（中心补红、外围压红）
- 结果：全屏绿解决，但**四角又红了**
- 原因：为了消除绿，把外围压红系数从 5/8 砍到 2/4，**力度减半**

### 第 3 版：恢复外围力度（+3/+1/−5/−8）
- 结果：仍偏红
- 原因：正圆等高线。左右边中点 r=638、上下边中点 r=360，**上下几乎没被补偿**

### 第 4 版：改成 16:9 椭圆 + 挪到 AWB 之前 ← **用户反馈"效果好"**
- `r² = dx² + 3·dy²`（两处对比：640² = 409600，3×360² = 388800，几乎相等）
- 上下边中点 zone 4 → **11**，终于也被补偿
- 挪到 AWB 之前后，AWB 能看到补偿结果并自动闭环均值
- **这是目前最好的版本**

### 第 5 版：8 档平滑 + 中心归零
- 发现中心 `+3` 就是"中间粉椭圆"的来源（`zone 0-3` 覆盖约 57%×58% 的半宽半高）
- 同时修正 `r2>>15` 会让四角饱和到 15 的问题（改 `>>16`，四角落到 zone 12）
- 结果：未单独验证

### 第 6 版：闭环自标定（shading_cal）
- 思路：测 tint 输出的中心/边缘 R/G 比值，闭环调一个总强度 K
- **两次失败**：
  1. 第一版判决逻辑有 bug —— 首次遇到"误差超上限"就锁死 `O_done`，之后再不看画面。用户反馈"没有作用"
  2. 修完 bug 后闭环真的转起来，但**画面全是黑线在跳**
- 推测原因：**没有阻尼**。K 一步就是 12% 幅度变化，60fps 下 0.1 秒内从 8 跳到 0 或 15，逐帧震荡叠加 DDR 帧缓存和 AWB 追踪，表现为横扫条纹
- 已回退

## 6. 如果继续做：推荐路线是「离线标定」，不是闭环

闭环的问题是不可控（会震荡），而且**看不见内部状态**。

### 推荐设计

1. **只测量，不控制**
   - 加 6 个累加器（中心区 / 边缘区 × R/G/B，26bit）
   - 约 **160 FF + 160 LUT + 2 DSP**
2. **把两个比值显示出来**（OSD 数字或网口）
   - `k_r = (Rc/Gc) / (Re/Ge)`，`k_b` 同理
   - 白纸挡镜头，读出这两个数
3. **换算成系数直接写死**
   - 形状表不变，幅度按测量值填
   - 然后**把测量模块删掉**，不留任何风险

### 关键要求

- **必须有读数**。没有读数就只能猜，这次已经证明了猜不出来。
- **不要在线闭环**。标定是一次性的，镜头固定，没有理由让它持续调整。
- 若确实要闭环，必须有：多帧平均、小步长（≤2%）、低通滤波、只在均匀画面更新。

## 7. 工程纪律（这几条是这次买的教训）

### 7.1 不要从照片或直觉编造空间校正系数

参考项目的 skill 文档原文：

> 固定的中心绿、边缘红不能仅靠全局白平衡保证修复……**空间校正需要均匀参考，不从照片任意编造系数**。

我前面 4 版都在编系数，全部失败。

### 7.2 眼睛不是测色仪器

人眼有色彩恒常性，盯着偏色画面十几秒就会把它当成"白"。这导致同一画面前后判断相反（"效果好" → "还是红"）。

**只要条件允许，就用数字判断，不要用观感判断。**

### 7.3 一次构建只动一个变量

成功的两版（第 4 版）恰好都不是"改数值"，而是**改结构**（位置 + 形状）。失败的都是改数值。

### 7.4 改 `isp_top.v` 前先确认行尾统一

文件曾混用 CRLF/LF（`write` 工具追加的模块是 LF）。后果：

- 按 `` `r`n `` 切分时整个模块被当成**一行**，按行号的脚本全部错位
- `Select-String` 仍然能搜到，所以**表象正常、实际出错**，很难发现

检查方法：

```powershell
$t=[System.IO.File]::ReadAllText($f)
"CRLF=$(([regex]::Matches($t,"`r`n")).Count)  单独LF=$(([regex]::Matches($t,"(?<!`r)`n")).Count)"
```

### 7.5 TD 推断 BRAM 的两个硬条件

`u_edge` 行缓冲始终进不了 ERAM，两次 `SYN-5105` 给出了不同原因：

1. 第一次：`cannot match any writemode` —— **RAM 读写套在带复位的 always 块里**
2. 拆出复位块后：`read address have no register` —— **读地址必须是寄存器**（我们的 `pf_addr` 是组合逻辑）

要满足第二条，读地址要打一拍，预取逻辑要整体重算（`pf_addr` 改成 `cur_addr + 2`），风险不小。

**结论**：`ram_style="bram"` 属性只在满足全部模板条件时有效；真的要用，直接例化 ERAM 原语更省事。
