# 决赛优化实施方案（feat/finals-opt）

> 依据：对 `feat/finals-opt` 分支源码的逐行分析 + `fpga/reports/final_area.rpt` / `final_timing.rpt` 实测数据 + 上位机实机跑测。
> 本文档只写"改哪里、为什么、代价多少"，不写泛泛建议。

## 0. 资源基线（所有 FPGA 改动的前提）

| 项 | 当前 | 余量 |
|---|---|---|
| Slice | 19070 / 21216（**89.88%**） | 2146 |
| ERAM | 80 / 108 | 28 |
| DSP | 39 / 40 | **1** |
| Setup WNS | +0.136 ns | 极紧 |
| Hold WNS | +0.020 ns | 极紧 |

面积口径（按 `final_area.rpt` 反推）：**1 LUT6 ≈ 1 slice，2 FF = 1 slice，1 块 ERAM 不占 slice**。所以「加 LUT 很贵、加 FF 半价、加 ERAM 不占 slice」。

## 2. 边缘检测（最高优先级）

### 2.1 诊断：不是"RGB 相加"

亮度加权本来就有：`isp_top.v:2046-2051` 用 `R/4 + G/2 + B/4`。真正的四个原因是：

| # | 机制 | 代码 | 实测影响 |
|---|---|---|---|
| 1 | 水平 2:1 降采样：灰度算完后相邻两像素求平均成 640 个 pair，再在 pair 网格上做 Sobel | `L2058-2061` | 1 px 竖线峰值 mag **504**（全分辨率 1012，**只剩 50%**） |
| 2 | 纯二值输出，丢梯度强度 | `L2112-2116` | 强弱边同白、无抗锯齿 |
| 3 | 无非极大值抑制 | 全文件无 | 每条边是 **4 px 宽白带**（全分辨率+NMS 为 2 px） |
| 4 | 单门限无滞回、固定在 80 | `L313-314` | 满量程 1020，门限仅 7.8%；暗部噪声被 gamma 放大 |

附带：整体 +2 px 水平错位、+1 行垂直错位（`L2138`、`L2143-2145`），边缘模式看不出来，但**卡通模式描边不贴色块**。

### 2.2 方案

**方案 1（低风险，先做）≈ +70 slice、0 ERAM**
1. `L2115-2116` 二值 → 强弱双阶：`strong ? 255 : min(127, mag>>1)`
2. 新增 `O_strong[3:0]` 给卡通用；**必须同步改 `L2274`**，否则卡通描边直接消失
3. 可选：`L2058-2061` pair 平均 → pair 取 max（1 px 响应 504→1012）

**方案 2（画质质变，净省面积）−50~−110 slice、+2 ERAM**
1. 行缓存 320×16 → 320×32（4 像素全分辨率），改**同步读**才能推断成 ERAM
   —— 现状 `ram_style="block"` 无效，根因就是异步读，实测 `u_edge` ERAM=0、DRAM=256
2. 6 列 × 3 行真 3×3，一拍算 4 个全分辨率 Sobel
3. 左邻 NMS：+11 FF + 4 比较器
4. 关键省钱点：**ERAM 读地址 = `x_grp+1`**，用 1 拍读延迟换对齐，主通路不加延迟

**方案 3（类 Canny）不建议**：+300~450 slice、+3~4 ERAM、再加 1 拍流水，固定机位室内演示收益有限。

### 2.3 已落地实现（2026-11-11，`feat/finals-opt`）

按方案 2 的简化版落地：**全分辨率 3×3 Sobel，不做 NMS**。

用位精确模型对比后发现：全分辨率**加**左邻 NMS 反而把笔画打成断线（text 图不一致率上升），
而全分辨率 + 直接二值在文字/细线上最干净。所以最终实现去掉了 NMS，比原计划更简单、更省面积。

| 项 | 旧 | 新 |
|---|---|---|
| 水平分辨率 | 相邻 2 像素平均成 pair（2:1 降采样） | **全分辨率 1280** |
| 行缓存 | 320×16，异步读 → 落到 DRAM（256 LUT） | 320×32，**同步读** → ERAM |
| Sobel | 每拍 2 个（pair 网格） | 每拍 **4 个**（6 列 × 3 行窗口，共用 6 个纵向加权和） |
| 输出 | 纯二值 | 纯二值（不变，卡通描边依赖 `0xffffff` 判据） |
| 延迟 | 1 拍 | **2 拍** |
| 空间偏移 | 右移 2 px、下移 1 行 | 右移 1 px、下移 1 行 |
| DSP | 0 | 0 |

同步读必然多一拍，所以 `raw_tdata_d` 后面追加了 `raw_tdata_d2` 一级，
卡通模式与裸图分支统一使用两拍延迟，画笔/描边仍然逐拍对齐。

**验证方式**（本机没有 Verilog 仿真器）：
- `fpga/tools/edge_compare.py` —— 各候选算法的位精确对比 + 出图
- `fpga/tools/edge_rtl_model.py` —— **周期精确**复刻新 RTL 的流水线（行缓存、行奇偶交换、
  读写时序、计数器），喂真实图像流后与 numpy 参考 Sobel 比对：
  - text 图：**0 像素不一致**（14727/14727 全同）
  - shapes 图：**0 像素不一致**
  - lines 图：8 像素不一致（0.01%，全部在边界屏蔽区）

**上板前必须确认**：综合报告里 `u_edge` 的 ERAM 用量应 ≥ 2、DRAM 应接近 0。
如果 TD 没有把 memA/memB 推断成 ERAM（例如显示成几千 LUT），说明推断失败，
不要继续布线，先把读端口写法调整成更标准的单写单读结构。

### 2.3 验收
- 主观：细线、文字轮廓可见，白边由 4 px 变 2 px
- 客观（可选）：位精确模型输出细线响应比 / 边缘宽度 / 定位误差

## 3. 色块识别准确率

### 3.1 现状
不是 HSV，也不是 8×8 分块（README 那段已过时）。实际链路：
`is_red/is_green/is_blue` RGB 主通道占比判据（`L703-744`：红 31.25%、绿 18.75%、蓝 25%）
→ 组内 `hit_cnt≥MIN_RUN`（红 3 / 绿 3 / 蓝 2）
→ 边缘屏蔽 → 轨迹表（NTRK=4、GAPX=16 px、GAPY=16 行）→ 帧末取面积最大的 rank1 → `AREA_TH=300`。

### 3.2 四个真 bug（按影响排序，改动都极小）

| # | 问题 | 位置 | 改法 | 代价 |
|---|---|---|---|---|
| 1 | CCL 版 `in_field` 退回"整圈屏蔽"，**丢掉 23.4% 画面** | `L1701-1704` | 照抄未实例化旧模块 `L1014-1016` 的"只屏蔽四角（1.56%）" | **0 LUT** |
| 2 | 轨迹永不合并，物体被高光撕开后两条轨迹各自面积减半 → 双双 <300 → **整块消失** | `L1740-1751`、`L1968-1990` | 匹配到多条时并入最低索引（cnt/bbox/Σx/Σy 相加） | ~90~120 LUT/色 |
| 3 | 无 valid 迟滞，面积在 300 附近**框逐帧闪** | `L1834-1842` | 加 `AREA_OFF = 0.7·AREA_TH` | ~10 LUT + 3 FF |
| 4 | `MIN_RUN` 被硬化成检测门（注释说只门控包围盒，那只对旧模块成立） | `L1706` | 轨迹更新用 MIN_RUN，面积/质心用 `hit_cnt!=0` | ~10 LUT |

次要：检测跑在 gamma 之后（`L256`），判据随亮度漂——挪到 gamma 前代价 0，但**要重标三个 margin 和 MIN_BRIGHT**，建议和上面一起做。

### 3.3 多色块（任务 6 的澄清）
**红/绿/蓝本来就是并行同时识别的**：三套独立 `color_box_ccl_96`（`L801-829`），各 4 条轨迹，三色框 + 质心十字 + 标签 + 三色 UART 都已在跑。
限制只有两条：① 每色只画 rank1（rank2-4 端口在但被裁掉）；② NTRK=4。

- 若场景是"红绿蓝各一个块"→ **已经支持，不用改**
- 若场景是"同色多个块"→ 恢复画 rank2-4 约 **+900 slice**，且历史上会出现"一个物体好多框"（轨迹撕裂），必须先修 3.2 的 #2
- 更便宜的替代：OSD 显示每色块数（`R:2 G:1 B:0`），约 +30 LUT

## 4. 小车跟随提速

### 4.1 延迟链路（实测推算，非仿真）
光子→轮子 ≈ **170~230 ms**：

| 环节 | 当前 | 证据 | 可压到 |
|---|---|---|---|
| 相机 | 60 fps = 16.7 ms | — | 不可压 |
| 检测结果打一拍 | +16.7 ms | `isp_top.v:1419` | 改 RTL 可省，高风险 |
| UART | 607 µs，占线 **3.65%** | `ColorTrack.c:20` | **不是瓶颈，不用动** |
| 目标更新 | **20 ms 轮询**，与 60 fps 拍频丢帧 | `Control.c:222` | 事件触发 <1 ms |
| dev 低通 | α=0.30 → τ=56 ms，90% 需 129 ms | `ColorTrack.h:76-77` | α=0.55 → τ≈21 ms |
| 命令斜率 | 5/20ms → 0→40 要 160 ms | `ColorTrack.h:78-79` | 12/20ms → 56 ms |
| 视觉控制律 | **纯 P + 死区，无 I 无前馈** | `ColorTrack.c:236-260` | 加 I/前馈 |
| 轮速环 | 增量式，满量程 125/e 秒 | `Pid.c:59-88` | 加前馈 + Kp↑ |
| 占空比上限 | 50%（`out_max=5000`） | `Pid.c:95` | 75% |

### 4.2 P0 前置：单位矛盾必须先标定
- `Control.h:74` `ENCODER_COUNT_TO_CM 0.486` + 20 ms 窗口 ⇒ 1 count/20ms = **24.3 cm/s**
- `Control.c:77` 注释 `10.0f // 4.9cm/s` ⇒ 约 2 unit = 1 cm/s
- `Control.h:25` `MAX_LINEAR_SPEED 80.0f` 标 cm/s，却直接加进轮速目标

三者互斥 ⇒ 速度环长期饱和，"速度闭环"实际是开环。**不标定就调参全是白调。**

台架动作：① 推车 100 cm 记四轮 Σcounts；② 抬轮给定 10/20/40/80 记稳态转速与占空比；③ 统一成 counts/20ms。

### 4.3 提速方案（按性价比）
1. 视觉环加积分/前馈（消稳态滞后，**这是"不跟手"主因**）
2. 滤波 α 0.30→0.55、斜率 5→12、死区 4→2
3. 速度环加前馈 + Kp 10→25~35 + out_max 7500
4. 帧到达触发替代 20 ms 轮询
5. 拆掉"到达全停"（`ARRIVE_W=85 < DIST_W−死区=87` 本身矛盾）
6. 上限：横移 40→55、前进 70→90

**"1.5 倍速"的正确理解**：不是把速度值乘 1.5，而是把应用侧延迟压到 **90~110 ms**（现在是 170~230 ms），观感自然快 1.5 倍。

## 5. 避障

车端**零**测距代码，现有传感器只有 4 路编码器 + IMU660RA + 电池 ADC。

| 方案 | 硬件 | 能力 | 建议 |
|---|---|---|---|
| 堵转 + 冲击检测 | 无 | 撞了才停 | **必做兜底**，~150 行 |
| 前向 HC-SR04 | 1 模块（注意 ECHO 5V 必须分压） | 2~250 cm，提前减速/停车 | **推荐** |
| ToF VL53L0X | 1~2 模块 I2C | 2 m，体积小 | 次选 |
| FPGA motion box 进 UART | 改 RTL + 重出 bit | 60 Hz，但静止障碍会整幅误报 | **不建议赛前** |

状态机：`NORMAL → SLOW → BRAKE → STRAFE（麦轮横移，不转车头，摄像头不丢目标）→ RECOVER`，冲击/堵转最高优先级，5 s 内触发 3 次锁存停机。

**安全补丁（与提速强相关）**：`Control.c:225` 只在 IMU 就绪时更新电机，IMU 失效时电机**保持上一次 PWM**，没有急停。建议把四轮 `Motor()` 更新移出该门控，异常时显式写 0。

## 6. 小屏 + 大屏

**关键事实：PH1P35 开发板只有一路 TMDS（HDMI）输出**（`design_top_wrapper.v:15-18` 的 `O_tmds_ch0/1/2/clk`），没有第二路显示端口，剩余资源也塞不下第二条视频通路。

- **方案 A（推荐）**：HDMI 1→2 分屏器（约 ¥50~100），一路接小车小屏、一路接展台大屏，显示同一画面。切到模式 5/6 时大屏就是 AWB 左右对比，`DEMO_GUIDE` 的演示流程不用改。
- **方案 B**：只有一块屏时，网页上位机做"模式镜像 + 讲解卡"，画面靠采集合成。
- **方案 C**：HDMI 采集卡（¥60~150）+ 网页 `<video>`，可以录制/截图留证，但采集卡有延迟，标注"监看，非算法输出"。

小屏选型注意：必须是 **HDMI 输入**且能接受 1280×720@60（大部分 5~7 寸 HDMI 屏都行），否则要改视频时序，代价是整个 video_out 重做。

## 9. 构建与验证约定

- 所有改动走 `feat/finals-opt` 分支，验证通过再合 `main`。
- 每轮 RTL 改动后必须重跑：综合 → 布局布线 → 核对 `Slice ≤ 19070`、`WNS ≥ +0.13 ns`、`ERAM ≤ 82`。
- 一个功能一个 bit，回退粒度清晰；bit 生成时间必须晚于源码改动。
- 未经上板验证的效果**不得**写进 README、演示视频或答辩材料。
